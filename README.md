# Trip Service

Сервис управления поездками **TripGo**.

**Лабораторная работа № 2: Архитектура, качество кода и observability.**

## Требования

- Go 1.26+
- Docker (для окружения `tripgoctl`)
- `tripgoctl` (утилита курса)
- `psql` (опционально, для проверки БД)

## Запуск

### 1. Поднять локальное окружение

Запуск PostgreSQL и OTel Collector:

```bash
cp environment.toml .
tripgoctl cluster start
tripgoctl environment start
```

### 2. Накатить миграции

```bash
make migrate
```

### 3. Запустить сервис

```bash
make run
```

### 4. Проверить работоспособность

```bash
curl -i localhost:8080/health
curl -i localhost:8080/ready
```

## Архитектура

Код разделен на слои с однонаправленными зависимостями: зависимости направлены внутрь.

| Слой | Назначение |
|---|---|
| `internal/domain` | Бизнес-правила (например, `trip.Finish`). Не зависит от HTTP, БД и OTel. |
| `internal/usecase` | Сценарии (создать, получить, завершить). Зависит только от домена и интерфейсов. |
| `internal/http` | хендлеры и middleware. Зависит от юзкейсов. |
| `internal/repository` | Работа с БД (`pgx` и `squirrel`). Зависит от домена. |
| `internal/infra` | Инфраструктура: БД, OTel, транзакции. |
| `internal/container` | Composition root — сборка всех зависимостей. |

Интерфейсы зависимостей объявлены на стороне потребителя (в `contract.go` юзкейсов и хендлеров).

Сборка всех зависимостей происходит в `container.New()`, который вызывается из `main.go`.

## Тесты

### Unit-тесты

Запуск unit-тестов без БД с проверкой на data race и покрытием:

```bash
make test
```

### Интеграционные тесты

Для запуска интеграционных тестов с PostgreSQL:

```bash
tripgoctl environment start
make migrate
make test-integration
```

### Покрытие тестами

- Домен — unit-тесты бизнес-логики.
- Юзкейсы — тесты с использованием `gomock`.
- Маппинг ошибок — проверка преобразования ошибок.
- Хендлеры — тестирование через `httptest`.
- Репозиторий — интеграционные тесты с реальной базой данных и проверкой отката транзакций.

## Что сделано в этой работе

- Код переложен по слоям (`domain`, `usecase`, `http`, `repository`, `infra`).
- Внешние зависимости скрыты за интерфейсами, объявленными в `contract.go` у потребителей.
- Настроен `.golangci.yml` со всеми линтерами.
- `make lint` выдает 0 issues.
- Написаны unit-тесты (домен, юзкейсы, хендлеры, маппинг ошибок) и интеграционные тесты (репозиторий).
- Покрытие `usecase` и `domain` - ок. 80-90%.
- Подключен OpenTelemetry:
  - трейсы (HTTP и БД через `otelpgx`);
  - метрики (`http.server.request.duration`, `tripgo.trips.created` и др.);
  - логи в JSON с `trace_id` и `span_id`.
- Настроен порядок middleware:

```text
Recover -> Tracing -> Logging -> Metrics -> Router
```

## Принятые решения

### 1. Менеджер транзакций

Менеджер транзакций остался контекстным.

`TxManager.Do` открывает транзакцию и кладет ее в `context.Value`. Репозитории достают транзакцию через `transaction.FromContext(ctx)`.

Бизнес-код (usecase) не знает про `pgx`.

### 2. Уровень изоляции транзакций

Выбран уровень изоляции **ReadCommitted**.

Защита от гонок обеспечена на уровне схемы (partial unique index на активные поездки) и атомарного `UPDATE ... WHERE status = 'active'`, а не за счет повышения уровня изоляции.

### 3. Запрет двух активных поездок

Запрет обеспечивается partial unique index в БД.

Ошибка `23505` ловится в репозитории и преобразуется в доменную ошибку `ErrDriverBusy`, которая в хендлере мапится в HTTP-ответ:

```http
409 driver_busy
```

### 4. Обработка ошибок

Все бизнес-ошибки возвращаются в формате `application/problem+json`.

- Доменные ошибки объявлены в `internal/domain/trip/errors.go`.
- Единый маппинг «доменная ошибка → HTTP-ответ» вынесен в `internal/http/domainerror`.

### 5. Экспорт телеметрии

Для отправки трейсов и метрик используются HTTP-экспортеры OTLP (`http/protobuf`), так как OTel Collector в локальном окружении настроен на этот протокол.

При недоступности коллектора сервис продолжает работать штатно: ошибки экспорта логируются, но не приводят к остановке процесса.
